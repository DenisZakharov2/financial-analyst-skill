## Средние

### 1. Монолитная `run()` в cli.py

`skills/financial-analyst/scripts/finanalyst/cli.py:398`–1162 — одна функция
на ~765 строк: загрузка, ПДн, метрики, прогноз, A/B, сегментация, отчёты.
Главный риск сопровождаемости. Рекомендация: разбить на стадии
(`_load_and_sanitize`, `_compute_sections`, `_extend_sections`, `_emit_reports`),
чтобы `run()` стал оркестратором, а стадии тестировались по отдельности.

### 2. Точные пины зависимостей в pyproject.toml

`pandas==2.2.3`, `numpy==1.26.4` и т.д. в `[project.dependencies]`. Для пакета,
который ставят через `pip install -e .` рядом с другими инструментами, это
почти гарантированный конфликт зависимостей. Точные версии уже есть в
`requirements.lock.txt`.

Рекомендации:

- в `pyproject.toml` — диапазоны (`pandas>=2.2,<3`);
- `numpy==1.26.4` не собирается на Python 3.13, а `requires-python = ">=3.10"`
  верхней границы не ставит: на 3.13 пользователь получит непонятную ошибку
  сборки. Стоит `requires-python = ">=3.10,<3.13"` или диапазон для numpy.

### 3. Выборочный скан ПДн пропускает середину таблицы

`finanalyst/pii.py`, `_detect_series_pii_type`: для больших таблиц сэмплируются
только `head(250) + tail(250)` строк. ПДн в середине таблицы (например, блок с
телефонами между чистыми данными) будет пропущен — при том, что режим `strict`
позиционируется как блокирующий gate.

Рекомендации: задокументировать ограничение в `references/quality-gates.md`;
лучше — случайный сэмпл по всем строкам (`series.sample(500, random_state=…)`)
или повышение лимита.

## Мелкие

### 4. Даты в будущем

`CHANGELOG.md` — «2.1.1 — 2026-11-12», `requirements.lock.txt` — «2026-11-10»,
`LICENSE` — 2026. Если опечатка — поправить.

### 5. Несогласованный комментарий в pii.py

Комментарий «segfault in pandas 2.2.3/numpy 2.1.3» упоминает numpy 2.1.3,
который не совпадает с пином 1.26.4. И это единственный английский комментарий
в русскоязычной кодовой базе (`references/style-ru.md` требует единообразия).

### 6. Дублирование логики шага прогноза

Пороги `300/170/80/27` дней повторяются в `metrics.forecast_trend`
(`finanalyst/metrics.py`) и в `_infer_step_months` (`finanalyst/metrics.py`).
Настройка одного места без второго — источник расхождения. Рекомендация:
одна функция-источник.

### 7. `check_srm` при отсутствии scipy

Возвращает `srm_ok: False, p_value: 0.0` — «проверка невозможна» неотличимо от
«проверка провалена». Честнее отдельный статус `srm_check_unavailable`.

### 8. Неочевидный ceil в `_checksum_threshold`

`finanalyst/pii.py`: `int(-(-0.25 * sample_size // 1))` — замаскированный
`math.ceil()`. Читаемость пострадала.

### 9. Производительность: iterrows

`finanalyst/seasonality_tat.py:319` — построение словаря по всей таблице sales
через `iterrows()`; на больших выгрузках заметно медленнее `set_index` /
`itertuples`. Для отчётных таблиц в `reporting.py` некритично.

### 10. CI

- нет `permissions: contents: read` (least privilege);
- нет `concurrency` для отмены устаревших прогонов;
- нет отчёта о покрытии — при 184 тестах было бы видно, какие модули
  (`reporting.py` на 49 КБ) покрыты слабее.

### 11. Дублирование pypdf

`pypdf` указан в основных зависимостях и в `dev`-extra (`pyproject.toml`).
В dev можно убрать.

## Что сделано хорошо

- Обработка ввода: автоопределение кодировок (utf-8-sig → cp1251) и
  разделителей; ошибки не глотаются, а возвращаются с exit code 2
  (`core.DataLoadError`).
- Статистика реализована грамотно: критерий Саттертуэйта, капча лага
  Грейнджера `T/5`, домножение p-value на число лагов перед FDR, Шепли для PAR.
- Безопасность: экранирование во всём HTML-дашборде, защита XLSX от formula
  injection (`=+-@`), HMAC-псевдонимы с сохранением join-ключей и честное
  предупреждение об эфемерном ключе.
- Тесты содержательные (2254 строк): проверяют контракты метрик и регрессии
  аудита, а не «что код запускается».
- Дисциплина версий: CHANGELOG, version в трёх местах согласованы (2.1.1),
  self-check в CI.
